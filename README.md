# Практична робота №5 — Адаптивний LUME

LUME — навчальний магазин смарт-речей для дому. Проєкт продовжує оформлену версію практичної №4: головну сторінку, вхід, реєстрацію й створення товару. У цій роботі CSS перероблено на mobile-first, додано Grid і content-driven media queries. HTML-файли та їхній DOM-порядок збережено без змін.

## Структура й запуск

```text
practical-05-lume/
├── index.html
├── login.html
├── register.html
├── product-form.html
├── styles/main.css
├── images/
├── README.md
└── .gitignore
```

Відкрийте `index.html` у браузері. Залежності, JavaScript і складання проєкту не потрібні. Усі сторінки використовують один `styles/main.css`. Файли пояснень і звіту не потрібні сайту й підготовлені окремо від цього репозиторію.

За основу взято відому локальну копію практичної №4. Якщо попередній проєкт додатково змінювався, ці зміни потрібно узгодити з поточною версією. Повноцінна серверна логіка ще не реалізована.

## Mobile-first база

Без width media queries header і hero мають послідовну вертикальну композицію. Вміст має fluid container:

```css
.container {
    inline-size: min(100%, 84rem);
    padding-inline: clamp(1rem, 3vw, 2rem);
    margin-inline: auto;
}
```

Заголовки й відступи масштабуються через clamp(), зображення та відео мають max-inline-size:100% і block-size:auto. Фактичних video або таблиць у цьому проєкті немає. Для зображень збережено width/height у HTML. Текстові блоки не мають fixed height; довгі слова переносяться через overflow-wrap:anywhere. Поля й flex/grid items можуть стискатися завдяки min-inline-size:0.

Основні дії не приховані на mobile. Навігація переноситься рядками, усі посилання залишаються доступними без JavaScript. Немає order, reverse directions, абсолютного позиціонування основного макета або overflow-x:hidden для маскування помилок. Absolute використано тільки для доступного skip-link, як у попередній роботі.

## Де використано Flexbox

- `.site-nav ul` і `.account-nav` — одновимірна навігація з wrap та gap.
- `.search-form` — підпис, поле пошуку й кнопка; controls переносяться за доступним місцем.
- `.catalog-tools` — пошук і кошик: колонка на вузькій ширині, рядок за достатнього місця.
- `.form-actions` — надсилання й скасування; на вузькому екрані займають окремі рядки, на ширшому розміщуються поруч.
- `.choice` — checkbox/radio та пов’язаний текст; DOM-порядок не змінюється.
- `.header-inner` — єдиний рядок бренду, меню й облікових дій на широкому екрані.

## Де використано Grid

Основний повторюваний вміст — каталог `.collection-list`:

```css
.collection-list {
    display: grid;
    grid-template-columns: repeat(auto-fit, minmax(min(100%, 15rem), 1fr));
    gap: 1.5rem;
}
```

`auto-fit` визначає кількість колонок за доступним простором, `minmax()` задає нижню межу та гнучкий максимум, а `min(100%,15rem)` дозволяє картці вміститися навіть у контейнер вужчий за 15rem. `1fr` рівномірно розподіляє місце між колонками. Остання картка неповного рядка зберігає ширину своєї колонки.

Hero також використовує Grid: базово одну колонку, пізніше — дві `minmax(0,1fr)`.

## Breakpoints та причини

| Умова | Зміна композиції | Обґрунтування |
|---|---|---|
| Базові стилі, менше 42rem | Header і hero послідовно; toolbar у колонку | Залишається читабельна ширина тексту й доступні дії на вузькому екрані |
| min-width:42rem, приблизно 672px за 16px | Hero — дві колонки; пошук і кошик — один рядок | Текстовий блок і картка товару вже мають достатню ширину для паралельного розташування |
| min-width:66rem, приблизно 1056px за 16px | Бренд, меню й облікові дії — один рядок; просторіший hero | Повна навігація вміщується поруч із брендом та обліковими діями |

Точки вибрано за вмістом, а не моделями пристроїв. Перевірено 671/672px та 1055/1056px — безпосередньо з обох боків умов. Grid каталогу змінює кількість колонок самостійно, без breakpoint на кожну кількість.

Окремий `prefers-reduced-motion: reduce` вимикає transitions. Він стосується системної переваги користувача й не рахується одним із двох width breakpoints.

## Три знайдені responsive-проблеми

| Проблема попередньої версії | Фактична перевірка | Виправлення |
|---|---|---|
| Нерівномірна ширина карток у неповному flex-рядку | При 900px перші три картки мали близько 263px, четверта — 836px | Каталог переведено на Grid. У новій версії при 900px усі чотири картки мають 266px |
| Надмірно вузькі поля через вкладені padding | При 320px поле назви товару мало ширину 164px | Зменшено бокові відступи mobile-контейнера, form-panel і fieldset; при 320px поле тепер 228px. На ширших екранах відступи збільшуються |
| Довге слово в описі картки викликало горизонтальне прокручування | При 360px тестовий нерозривний опис збільшував scrollWidth сторінки на 1017px понад viewport | Додано overflow-wrap:anywhere і гнучкі обмеження Grid/items. Той самий тест тепер дає overflow=0 |

Зі звичайним коротким вмістом попередня версія не мала overflow на цих контрольних ширинах. Третя проблема виявлена саме stress-тестом довгого вмісту. Помилки не маскувалися через приховування горизонтального overflow.

## Перевірені ширини та результати

Перевірено всі чотири сторінки на **320, 360, 390, 430, 671, 672, 768, 900, 1055, 1056, 1280 та 1440px**. Дата: 19 жовтня 2026 року. Браузер: Microsoft Edge 155.0.4283.62.

- 375 адаптивних перевірок — успішні. Немає горизонтального overflow, кнопки й controls у межах viewport, навігація не прихована, порядок елементів не переставлено.
- 65 перевірок семантики й форм — успішні: label, aria-describedby, required, email, довжини, ціна, категорія, radio/checkbox, Enter, Space, Tab, FormData.
- Перевірено дуже довгу назву й опис, порожній каталог та список із 40 карток. Тестовий вміст змінювався тільки в браузері; у файлах залишено початкові чотири товари.
- Справжній browser zoom **200%** перевірено на всіх чотирьох сторінках у тестовому профілі. За однакового фізичного вікна viewport змінився з 1416px при 100% на 708px при 200%, devicePixelRatio — з 1 на 2. Overflow залишився 0; кнопки надсилання й скасування доступні.
- Перевірено клавіатурний focus і skip-link. Немає overflow-контейнерів, що обрізають фокус. Checkbox/radio залишаються нативними, а їхні підписи мають зручну область активації.
- Кнопки та основні навігаційні дії мають мінімальну висоту 44px. На mobile дії форми переносяться без приховування.
- Reduced motion перевірено через емуляцію системної переваги: transition-duration стає 0s.
- HTML-файли байтово ідентичні версії практичної №4; семантика й DOM-порядок збережені. Нової віддаленої перевірки Nu HTML Checker для цієї версії не виконували.

Це браузерні перевірки, а не повний WCAG-аудит. Фізичні mobile-пристрої, скринридер та всі браузери не перевірялися. Числові результати й скриншоти містяться в окремих матеріалах звіту.

## Збережені форми та GET/POST

| Сторінка | Метод | action | Призначення |
|---|---|---|---|
| index.html | GET | index.html | Пошук; search потрапляє в URL, фільтрація каталогу ще не реалізована |
| login.html | POST | api/login | Майбутній вхід; пароль не потрапляє у query string |
| register.html | POST | api/register | Майбутня реєстрація |
| product-form.html | POST | api/products | Майбутнє створення товару |

Шляхи API відносні до папки проєкту й умовні. Без Backend дані не зберігаються; на статичному сайті після коректного submit можлива помилка маршруту. POST сам не шифрує дані — для захисту передавання потрібен HTTPS. Підтвердження пароля HTML не порівнює з першим паролем. Авторизації й перевірки прав адміністратора ще немає. Використовуйте лише вигадані облікові дані.

Збережено autocomplete=email, current-password, new-password і nickname відповідно до змісту полів. Підказки пов’язані через aria-describedby. Required, обмеження й помилки передаються текстом, а не лише кольором.

У Console для перегляду form data без надсилання:

```js
console.table([...new FormData(document.querySelector("form")).entries()]);
```

Це діагностична команда DevTools, а не JavaScript у файлах сайту. Непозначені checkbox не включаються; кілька кольорів утворюють кілька пар finishes=value. Backend повинен повторно перевіряти всі дані, оскільки HTML-валідацію можна обійти.
